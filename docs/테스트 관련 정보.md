## 테스트 최적화 전략

### Spring Context 관리
* `AbstractXxxTest`마다 **Spring 컨텍스트를 한 번만 로드**합니다.
* `AbstractXxxTest`를 상속하는 테스트 클래스들은 동일한 컨텍스트를 **공유**합니다.
* 단, 테스트 내부에서 `@MockkBean`을 선언하면 **컨텍스트 캐싱이 무효화**되어 새로운 컨텍스트가 생성됩니다.
* 이를 방지하기 위해 다음과 같은 전략을 사용합니다:
  * 필요한 경우 `@MockkBean`은 `AbstractXxxTest` 내부에 선언합니다.
  * 또는 테스트 대상 객체에 대해 **Fake 객체**를 사용합니다.

## 테스트 데이터 초기화 전략
* 본 프로젝트에서는 테스트 데이터 초기화 전략으로 다음 세 가지 방법을 고려했습니다.

### 1. @Transactional
* 테스트 메서드에 `@Transactional`을 적용하여, 테스트가 종료되면 자동으로 롤백됩니다.
* 설정이 가장 간단하며 단일 트랜잭션 흐름에는 문제없이 동작합니다.
* 단, 다음과 같이 트랜잭션과 관련된 코드에서는 문제가 발생할 수 있습니다:
  * 테스트 코드와 실제 코드의 `@Transactional` 설정이 다를 경우
  * 트랜잭션 전파 레벨을 커스텀하는 경우
  * `TransactionalEventListener`를 사용하는 경우

### 2. @BeforeEach / @AfterEach
* 테스트 케이스 실행 전,후에 모든 Repository에 대해서 `deleteAll()`하도록 설정합니다.
* 이는 테스트 클래스가 늘어날 때마다 추가해야 하는 번거로움이 있습니다.
* 또한, FK 제약이 있는 경우 삭제 순서를 고려해야 합니다.

### 3. DataCleaner
* JPA 기준 `EntityManager`를 통해 모든 테이블을 `TRUNCATE`하도록 구현합니다.
* `deleteAll()`은 row 단위로 삭제하는 반면, `TRUNCATE`는 테이블 단위로 삭제하므로 성능이 좋습니다.
* 참조 무결성 제약 조건을 무시하는 방법을 사용하여 테이블 간의 삭제 순서를 신경쓰지 않아도 됩니다.
* 단, 테이블이 많을 경우 성능이 저하될 수 있습니다. 
  * `TRUNCATE`는 서로 간섭하지 않기 때문에 이 경우 병렬로 수행하여 해결할 수 있습니다. 


`@Transactional`방식은 간편하지만, 트랜잭션을 비즈니스 로직의 일부로 보고 그 동작 자체를 함께 검증해야 한다는 목표에 적합하지 않다고 판단했습니다.

`Before/AfterEach` 방식은 유지보수 비용이 높아 배제했으며, 

결과적으로 `DataCleaner` 방식을 채택하여 데이터를 정리하도록 구현했습니다.
